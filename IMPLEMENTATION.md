# Minotaur — план реализации

## 1. Назначение

Минималистичное Windows-приложение для первичной настройки компьютера. Администратор вводит имя компьютера, выбирает профиль и запускает настройку. Приложение переименовывает компьютер, выполняет действия профиля, при необходимости продолжает работу после перезагрузки и сохраняет сведения об оборудовании.

Главный принцип: настройка описывается данными. Нельзя зашивать состав профиля в интерфейс или один большой PowerShell-скрипт. Любое действие можно добавить из шаблона, изменить, отключить, удалить, скопировать и переставить в допустимых пределах.

## 2. Стек и границы первой версии

- Tauri 2: окно приложения, доступ к Windows, запуск исполнителя.
- TypeScript и простой веб-интерфейс: формы, редактор профилей, ход выполнения. Для небольшого интерфейса достаточно Svelte либо обычного TypeScript.
- PowerShell Windows: выполнение административных действий и сбор инвентаризации. Не требовать установленного PowerShell 7.
- JSON: профили, шаблоны, состояние запуска, отчёты.
- HTML: читаемая версия итогового отчёта.

Первая версия работает локально на Windows 10/11 x64. Централизованный сервер, удалённое управление, доменные учётные записи и автоматическое обновление приложения не входят в первую версию. Установщик должен предусматривать наличие WebView2; для автономной работы зависимости и установщики программ поставляются заранее.

## 3. Минималистичный интерфейс

### Основной экран

1. Поле «Имя компьютера» с текущим именем по умолчанию.
2. Список «Профиль» и короткое описание выбранного профиля.
3. Предпросмотр включённых действий.
4. Кнопка «Начать настройку».
5. Небольшая кнопка «Профили» для перехода к редактированию.

Во время выполнения показывать текущий шаг, количество завершённых шагов и раскрываемый журнал. Статусы: ожидает, выполняется, выполнено, пропущено, ошибка, требуется перезагрузка. Не показывать выдуманный процент внутри установки, если установщик его не предоставляет.

После завершения показывать итог, путь к отчёту и кнопки «Открыть отчёт» и «Новая настройка». При сбое — причину, доступные варианты восстановления и журнал.

### Редактор профиля

Слева список профилей, справа название, описание и упорядоченный список действий. Для действия доступны: включение, редактирование, копирование, удаление и перемещение. «Добавить действие» открывает каталог шаблонов. Редактор параметров строится по схеме выбранного шаблона.

Технические настройки и текст собственного сценария спрятаны в раскрываемую секцию. Изменения сохраняются явно; перед выходом с несохранёнными изменениями показывается предупреждение.

## 4. Модель шаблонов и профилей

Шаблон — описание типа действия: поля формы, проверка параметров, логика проверки результата и выполнения. Действие — экземпляр шаблона с конкретными параметрами. Профиль — список таких действий.

Каждый шаблон содержит:

- `id`, `version`, название, описание и категорию;
- JSON Schema параметров и подсказки для формы;
- требования: права администратора, сеть, файлы, зависимости;
- проверку уже выполненной настройки;
- обработчики выполнения и проверки результата;
- допустимые коды завершения, тайм-аут и правила перезагрузки;
- признак допустимости повторного выполнения и восстановления после прерывания;
- перечень секретных параметров, которые нельзя сохранять в журнале.

Начальный каталог:

| Шаблон | Основные параметры |
| --- | --- |
| Переименование компьютера | Новое имя, по умолчанию из стартового экрана |
| Создание локального пользователя | Имя, отображаемое имя, группы, ссылка на секрет |
| Установка MSI/EXE | Источник, аргументы, SHA-256, способ проверки установки |
| Установка через winget | Идентификатор пакета, источник, версия при необходимости |
| Настройка реестра | Раздел, имя, тип, значение, область пользователя/компьютера |
| Копирование файла | Источник, назначение, политика замены |
| Настройка службы | Имя службы, тип запуска, требуемое состояние |
| PowerShell-сценарий | Файл сценария, схема входных параметров, проверка результата |
| Инвентаризация | Состав сведений и каталог отчётов |

Любой пункт настройки должен быть представлен действием, включая переименование и инвентаризацию. Новый профиль получает их автоматически. Редактор разрешает менять их параметры и заменять реализацию совместимым шаблоном; проверка профиля требует ровно одного переименования и одной итоговой инвентаризации. Это сохраняет обязательный сценарий продукта без скрытых действий.

Шаблоны имеют версии. Профиль ссылается на конкретную версию; обновление шаблона не меняет существующие профили автоматически. Пользователь может скопировать шаблон и создать свой. Собственные шаблоны хранятся отдельно от встроенных.

Пример профиля:

```json
{
  "schemaVersion": 1,
  "id": "office",
  "name": "Офис",
  "description": "Базовое рабочее место",
  "steps": [
    {
      "id": "rename",
      "template": "windows.rename-computer",
      "templateVersion": "1.0.0",
      "enabled": true,
      "parameters": { "name": "${run.computerName}" },
      "onError": "stop"
    },
    {
      "id": "install-app",
      "template": "windows.install-package",
      "templateVersion": "1.0.0",
      "enabled": true,
      "dependsOn": ["rename"],
      "parameters": {
        "source": "assets/installers/example.msi",
        "arguments": ["/qn", "/norestart"],
        "detect": { "type": "msi-product-code", "value": "<PRODUCT-CODE>" }
      },
      "onError": "stop"
    },
    {
      "id": "inventory",
      "template": "windows.inventory",
      "templateVersion": "1.0.0",
      "enabled": true,
      "parameters": { "formats": ["json", "html"] },
      "onError": "stop"
    }
  ]
}
```

Подстановка `${run.computerName}` выполняется как значение параметра, а не вставка текста в PowerShell-код. Поддерживать только явный список переменных. Зависимости проверяются на циклы; инвентаризация запускается после остальных действий и необходимых перезагрузок.

## 5. Исполнитель

Интерфейс передаёт исполнителю идентификатор профиля и входные значения. Исполнитель проверяет профиль и создаёт неизменяемый снимок профиля, шаблонов и сценариев для конкретного запуска. Редактирование профиля во время выполнения влияет только на следующие запуски.

Алгоритм каждого действия:

1. Проверить зависимости и входные параметры.
2. Проверить, достигнуто ли требуемое состояние. Если да — пропустить действие с пояснением.
3. Сохранить состояние «выполняется».
4. Выполнить обработчик с тайм-аутом и сбором вывода.
5. Проверить фактический результат.
6. Сохранить статус и потребность в перезагрузке.

Передавать параметры через структурированный JSON, запускать процессы с отдельными аргументами. Не собирать команды конкатенацией пользовательского ввода. Для установщиков задавать проверку результата: MSI ProductCode, версия файла, запись установленной программы или специальный проверочный сценарий.

Первую версию выполнять последовательно. Настройка `onError`: остановить запуск или продолжить независимые шаги. Зависимые от упавшего шага действия блокируются. Любая ошибка обязательного шага исключает итоговый статус «успешно».

События исполнителя: `run.started`, `step.started`, `step.output`, `step.finished`, `run.rebootRequired`, `run.finished`. Каждое содержит `runId`, время и, при необходимости, `stepId`. Стандартный вывод сценария не смешивать с протоколом событий.

Отмена означает остановку перед следующим шагом. Прерывать работающий установщик можно только при явной поддержке шаблоном. Автоматический откат всей настройки не обещать: для действий с откатом он реализуется отдельно.

## 6. Переименование и перезагрузка

Для первой версии принять консервативные имена: 1–15 латинских букв, цифр и дефисов, без дефиса по краям и без имён только из цифр. Проверять до запуска. Если имя уже совпадает, действие пропускается.

Переименование обычно требует перезагрузки. Исполнитель различает запрошенное и фактическое имя. Шаги, требующие уже применённого имени, выполняются после перезагрузки. Другие действия можно завершить до неё, если их шаблоны это разрешают.

Состояние сохраняется атомарно после каждого перехода. Для возобновления используется временная задача Планировщика Windows с необходимыми правами. После входа администратора приложение подключается к состоянию запуска. Задача запускает только доверенный исполнитель с идентификатором сохранённого запуска; после завершения удаляется.

Секреты не помещаются в аргументы задачи или открытый JSON. Для нужных после перезагрузки секретов использовать защищённое хранилище с ограниченным доступом и понятной моделью учётной записи; если это не реализовано, запрашивать их повторно.

После неожиданного завершения статус «выполняется» означает неизвестный результат. Сначала повторная проверка состояния, затем повтор только для безопасно повторяемых действий. Для остальных требуется решение администратора. Не запускать произвольный сценарий повторно вслепую.

## 7. Инвентаризация и отчёты

Собирать через PowerShell/CIM: фактическое имя, производителя и модель, серийный номер и UUID, процессор, модули памяти, диски и их серийные номера, плату, BIOS, сетевые адаптеры, версию Windows. Отсутствующие значения отмечать как неизвестные. Не считать UUID или серийный номер гарантированно уникальными: некоторые устройства возвращают заглушки.

В отчёт также включать `runId`, время с часовым поясом, профиль и его версию/хеш, результаты действий и перезагрузок. JSON — источник данных, HTML строится из него с экранированием значений.

Имя файла: `OFFICE-023_2026-11-10_143025_<runId>.json` и соответствующий `.html`. Каталог задаётся в настройках, по умолчанию внутри `%ProgramData%\Minotaur\reports`. Если сетевой каталог недоступен, сохранять локально и показывать, что копирование не выполнено.

При сбое настройки также сохранять отчёт со статусом ошибки, если сбор сведений возможен. Успешный итоговый отчёт создаётся после проверки нового имени и завершения обязательных действий.

## 8. Структура проекта и данных

```text
src/                         интерфейс
src-tauri/                   интеграция с Windows и запуск исполнителя
executor/                    последовательность действий и протокол событий
templates/builtin/           встроенные схемы и PowerShell-обработчики
profiles/examples/           примеры профилей
assets/installers/           локальные установщики при необходимости
docs/                        описание форматов и шаблонов
```

Рабочие данные хранить в `%ProgramData%\Minotaur`: `profiles`, `templates`, `runs`, `reports`, `logs`. Файлы сценариев и возобновления, которые выполняются с повышенными правами, доступны на изменение только администраторам и SYSTEM. Обычный пользователь не должен иметь возможности подменить их перед продолжением запуска.

Редактирование и импорт профилей выполняются администратором. Импорт проверяет схему, версии, ссылки на шаблоны и пути. Профили со своими сценариями показывают эти действия в предпросмотре. Пароли в экспорт не включаются.

## 9. Этапы реализации и критерии готовности

### Этап 1. Контракты данных

Создать схемы профиля, шаблона, запуска, события и отчёта. Подготовить один пример профиля. Описать правила зависимостей, ошибок и перезагрузки.

Готово: валидатор принимает корректный профиль и объясняет ошибки неизвестных шаблонов, параметров и циклических зависимостей.

### Этап 2. Каркас интерфейса

Сделать основной экран, редактор списка действий и экран результата. Подключить имитацию выполнения без изменения Windows.

Готово: можно создать профиль, добавить действие из шаблона, изменить параметры и увидеть имитацию полного запуска.

### Этап 3. Исполнитель и состояние

Реализовать последовательное выполнение, события, тайм-ауты, журнал, атомарное сохранение состояния и неизменяемый снимок запуска. Добавить безопасные демонстрационные шаблоны проверки и записи файла.

Готово: интерфейс показывает реальные события; сбой и повторный запуск не теряют состояние; ошибки обязательных шагов отражаются в результате.

### Этап 4. Права и переименование

Добавить повышение прав через UAC, проверку имени, переименование и проверку текущего состояния. Проверять на виртуальной машине.

Готово: совпадающее имя пропускается, неверное отклоняется, новое имя корректно фиксируется как ожидающее перезагрузки.

### Этап 5. Возобновление после перезагрузки

Добавить задачу продолжения, восстановление запуска и проверку шагов с неизвестным результатом. Проверить права доступа к рабочим файлам.

Готово: после перезагрузки выполнение продолжается без повторного создания пользователей и повторной установки завершённых пакетов; временная задача удаляется.

### Этап 6. Основные шаблоны

Реализовать пользователей, MSI/EXE, winget, реестр, файлы, службы и собственные сценарии. Для каждого определить проверку результата и возможность повторного запуска. Для HKCU явно указывать целевого пользователя: процесс администратора может работать с другим профилем.

Готово: каждое действие настраивается через форму, создаётся из шаблона и корректно распознаёт уже выполненную настройку.

### Этап 7. Полный редактор

Добавить создание и копирование профилей, перемещение действий, создание пользовательского шаблона из существующего, импорт и экспорт. Собственный сценарий получает параметры через схему, как встроенный шаблон.

Готово: новый профиль и новое действие можно создать без изменения исходного кода приложения. Несовместимое обновление шаблона не ломает сохранённые профили.

### Этап 8. Инвентаризация

Добавить сбор сведений, JSON и HTML, настройку каталога и локальное сохранение при недоступной сети.

Готово: отчёт содержит применённое имя компьютера, дату, оборудование, выбранный профиль и достоверный результат каждого шага.

### Этап 9. Проверка и поставка

Собрать Windows-установщик. Проверить на чистых виртуальных машинах Windows 10/11, включая отсутствие WebView2, автономный запуск с локальными пакетами и работу без установленной среды разработки.

Обязательные сценарии: отказ UAC, отсутствующий установщик, неверный хеш, ошибка и тайм-аут установки, код требования перезагрузки, перезапуск приложения, неожиданная перезагрузка, повтор профиля, недоступный каталог отчётов. Отдельно проверить отсутствие паролей в журналах и экспорте.

Готово: полный сценарий «имя → профиль → настройка → перезагрузка → отчёт» проходит на чистой машине, повторное выполнение не дублирует уже достигнутые настройки.

## 10. Рекомендуемый порядок выпуска

Первый рабочий прототип: один редактируемый профиль, переименование, установка локального MSI, инвентаризация и продолжение после перезагрузки. После проверки этого сквозного сценария расширить каталог шаблонов и редактор. Это позволяет рано проверить самую сложную часть — надёжное выполнение и восстановление состояния.
